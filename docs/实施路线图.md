# 静电薄膜电机 / 静电吸附 科研知识助手 —— 实施路线图

**目标**：把现有的「PDF + SQLite 全文索引 + CLI」升级为「混合检索 RAG 网页助手」，本地 VSCode 开发 → GitHub 托管 → Render 部署。

**技术选型**（已确认）：混合检索（FTS5 + 向量）· DeepSeek/通义千问 · 仅索引上云、PDF 留本地 · FastAPI + 单页 HTML

---

## 0. 现状盘点

| 资产 | 规模 | 处置 |
|---|---|---|
| `文献库索引.db` | 13 MB，195 篇 papers、3547 个 chunks（平均 1614 字符，总 573 万字符） | 改名后入 Git |
| `PDFs/` | 285 个文件，770 MB | `.gitignore`，只留本地 |
| `ask.py` | FTS5 命令行检索 | 重构为 `retrieval.py` 的关键词分支 |
| 两个 `.xlsx` 目录 | 0.7 MB | 入 Git（作为元数据备份） |

**关键结论**：3547 chunks × 1024 维 float32 = **约 14 MB**。这个量级不需要任何向量数据库 —— 一个 `.npy` 文件 + numpy 矩阵乘法即可，单次检索 < 1 ms，内存占用 14 MB，Render 免费层的 512 MB 绰绰有余。这是本项目最重要的简化。

数据总量 = 13 MB（db）+ 14 MB（向量）≈ **27 MB**，可以直接进 Git 仓库，不需要外部对象存储、不需要 Render 付费磁盘。

## 阶段 1 · 建向量层（1 天）

### 1.1 先决定要不要重新切分

现在每个 chunk 平均 1614 字符（约 400 token）。这个粒度**能用但偏粗** —— 检索命中后送给大模型的上下文里会混入不相关内容。建议：

- **先不改**，用现有 chunk 跑通全流程；
- 上线后如果发现回答"抓不住重点"，再重新切分成 600–800 字符 + 150 字符重叠，重跑一遍 embedding（成本 < 1 元，无痛）。

先跑通比先做对更重要。

### 1.2 embedding 模型与成本

用阿里云百炼（DashScope）的 `text-embedding-v4`：

| 项 | 值 |
|---|---|
| 默认维度 | 1024（可选 64–2048） |
| 单次最多 | **10 条**文本，每条 ≤ 8192 token |
| 单价 | ¥0.0005 / 千 token（Batch 异步接口半价） |
| 语种 | 中英混合无压力，100+ 语种 |

语料 573 万字符、以英文为主，约 **140 万 token → 全库 embedding 约 ¥0.7**。开通百炼有免费额度，实际大概率不花钱。重跑十次也无所谓。

**一个容易漏的参数**：`text_type`。文献检索是**非对称任务**（短问句 vs 长段落），入库时用 `text_type="document"`，查询时用 `text_type="query"`，检索效果会明显好于两边都用默认值。

### 1.3 `scripts/build_vectors.py`

逻辑：

1. 从 `library.db` 按 rowid 顺序读出全部 3547 条 chunk 文本；
2. 每 10 条一批调 embedding API（注意批大小上限就是 10）；
3. 结果 L2 归一化后堆成 `(3547, 1024)` 的 float32 数组；
4. 存 `data/vectors.npy`，同时存 `data/vector_ids.json` 记录「第 i 行 ↔ 哪个 chunk rowid」的映射。

**必须做断点续传**：把已完成的批次写进临时文件，中途网络断了能接着跑。3547 条 ÷ 10 = 355 次请求，串行大概 5–10 分钟。

**归一化很关键**：归一化之后余弦相似度就等于点积，检索时一行 `vectors @ query_vec` 就出全部分数，代码和性能都最优。

## 阶段 2 · 混合检索 + RAG 后端（2 天）

### 2.1 检索融合用 RRF

FTS5 的 BM25 分数和向量余弦分数量纲完全不同，直接加权相加需要调归一化参数，很脆。用 **RRF（倒数排名融合）** 更稳，只看排名不看分数：

```
score(chunk) = Σ  1 / (k + rank_in_that_list)      # k 取 60
```

流程：关键词路取 top 30，向量路取 top 30，RRF 融合后取 top 8 送给大模型。

**保留 tier 过滤**：现有的 `①核心·薄膜电机`（142 篇）/ `②静电电机/机械`（45）/ `③电粘附/夹持`（6）/ `④外围`（2）分级是很有价值的信号。前端给一个「只搜①核心」开关，后端在两路检索里都加 tier 条件。

### 2.2 大模型层做成可切换

`app/llm.py` 里写一个 provider 抽象。DeepSeek 和通义千问都提供 OpenAI 兼容接口，所以其实只是换 `base_url` + `model` 两个环境变量的事：

```python
# 伪代码
client = OpenAI(api_key=..., base_url=BASE_URLS[provider])
resp = client.chat.completions.create(model=MODELS[provider], messages=[...], stream=True)
```

问答成本：每问送 8 段 × 约 400 token ≈ 4000 token 上下文，DeepSeek 约 **¥0.005/问**。一天问一百次也就五毛钱。

**注意 embedding 和 chat 是两家**：DeepSeek 不提供 embedding 接口。所以 embedding 固定走百炼，chat 可在 DeepSeek / 通义之间切。两个 API Key 都要配。

### 2.3 提示词：科研场景必须可溯源

这是学术工具和玩具的分界线。系统提示里硬性要求：

- 每个论断后面标 `[编号]`，编号对应召回段落；
- 检索结果里没有的内容，明确说"文献库中未找到相关证据"，**不许补脑**；
- 涉及具体数值（推力密度、击穿场强、驱动电压、间隙）时，必须连同实验条件一起引用 —— 静电驱动的性能数据脱离气压、介质、电极间距就没有意义；
- 回答末尾列参考文献：`标题 (作者, 年份, 期刊) · 第 N 页 · DOI`。

API 返回的 JSON 里每条引用都带 `file / page / title / authors / year / doi / tier`，前端才能渲染成可点的引用卡片。

### 2.4 接口设计

```
GET  /api/stats           库统计（论文数/段落数/年份跨度/分级分布）
POST /api/search          纯检索，返回带出处的段落列表
POST /api/ask             RAG 问答，SSE 流式返回
GET  /api/paper/{file}    单篇论文元数据 + 该篇全部段落
```

`/api/ask` 用 **SSE 流式**输出。不只是体验问题 —— Render 免费层冷启动慢，流式让用户第一秒就看到字，感知上完全不同。

### 2.5 启动时加载

`vectors.npy`（14 MB）在应用启动时 `np.load` 进内存一次，之后所有请求复用。SQLite 连接用 `check_same_thread=False` 并按请求开连接（SQLite 读并发没问题）。

## 阶段 3 · 前端单页（1 天）

一个 `app/static/index.html`，纯原生 JS，不上构建工具（没有 npm、没有打包步骤 = Render 部署少一半麻烦）。

结构：

- 顶部：搜索框 + 模式切换（检索 / 问答）+ tier 筛选 + 年份范围
- 中部：流式渲染的回答区，`[1] [2]` 角标可点击滚动到对应引用
- 下部：引用卡片列表 —— 标题、作者年份期刊、tier 徽章、页码、原文片段（关键词高亮）、DOI 链接
- 侧边：库统计（195 篇 / 3547 段 / 1970–2026）

**「打开 PDF」按钮的处理**：线上没有 PDF 文件。做成两个动作 —— 「查看原文段落」（展开数据库里的全文片段，线上可用）和「DOI 原文」（跳出版商）。本地跑的时候，读环境变量 `LOCAL_PDF_ROOT`，如果有值就额外显示一个直接打开本地 PDF 的按钮。同一套代码，本地功能更全。

要点：

- **仓库设为 Private**。文献 PDF 虽然没上传，但数据库里含出版商版权全文片段，公开仓库有法律风险。
- 27 MB 的二进制文件入 Git 没问题（GitHub 单文件警告线 50 MB、硬限 100 MB）。但**每次重建索引都会在 Git 历史里再压一份 27 MB**。所以：索引重建不频繁就直接 commit；如果发现要频繁重建，再改用 GitHub Releases 挂附件、部署时下载。
- 先 `git add .` 之后、`git commit` 之前，务必 `git status` 确认 `PDFs/` 和 `.env` 没被加进去。

```bash
git add .
git status                    # ← 检查！
git commit -m "init: 混合检索知识助手"
git branch -M main
git remote add origin git@github.com:<你的账号>/esfm-assistant.git
```

## 阶段 5 · Render 部署（半天）

`render.yaml`：

```yaml
services:
  - type: web
    name: esfm-assistant
    runtime: python
    plan: free
    buildCommand: pip install -r requirements.txt
    startCommand: uvicorn app.main:app --host 0.0.0.0 --port $PORT
    envVars:
      - key: PYTHON_VERSION
        value: "3.11"
      - key: DASHSCOPE_API_KEY
        sync: false      # 在 Render 面板手填，不进仓库
      - key: DEEPSEEK_API_KEY
        sync: false
      - key: LLM_PROVIDER
        value: deepseek
```

步骤：Render → New Web Service → 连 GitHub 仓库 → 授权 Private 仓库 → 自动读 `render.yaml` → 在 Environment 面板填两个 API Key → Deploy。之后每次 `git push` 自动重新部署。

### Render 免费层的三个硬约束

1. **`--port $PORT` 不能写死端口**。这是部署失败最常见的原因 —— 硬编码 8000 会一直显示 "Port scan timeout"。
2. **15 分钟无流量就休眠，唤醒约 1 分钟**。自己用可以忍；要给导师或组里同学演示，提前 2 分钟先访问一次唤醒。或者升 Starter（$7/月）取消休眠。
3. **512 MB 内存 / 0.1 CPU**。我们的 14 MB 向量 + 13 MB db 完全够用 —— 前提是**别装 torch / sentence-transformers / faiss**。embedding 走 API 就是为了这个。requirements.txt 里只该有 fastapi、uvicorn、numpy、openai、python-dotenv 这几个。

**磁盘是临时的**：容器重启后写入的文件全丢。所以数据必须来自 Git 仓库（我们正是这么做的），任何"运行时生成并保存"的想法（缓存、用户笔记、对话历史）都需要外部存储 —— 要做的话用 Render 免费 PostgreSQL 或 Supabase。

## 阶段 6 · 验证与迭代

**上线前必须做的一件事：建一个 20 题的评测集。**

从你自己的研究问题里挑 20 个，人工标注每题应该命中哪几篇论文，写个脚本算召回率。这样后面每次调参（chunk 大小、RRF 的 k、召回条数、要不要加 rerank）都有客观依据，而不是凭感觉。这一步花两小时，能省掉后面几周的反复折腾。

题目要覆盖：

- 具体数值型 —— "静电薄膜电机的推力密度典型值范围"
- 机理型 —— "电极间距如何影响击穿电压"
- 对比型 —— "感应式和同步式静电电机的效率差异"
- 中文提问检英文文献 —— "介电泳驱动的响应速度"（专门验证向量层是否真的起作用）
- 人物/沿革型 —— "Higuchi 组双激励方案的演进"

后续可加的功能，按性价比排序：

1. **查询改写** —— 大模型先把中文问题扩成英文同义词组再检索，对中文提问召回提升最大，实现成本最低
2. **稀疏向量** —— `text-embedding-v4` 支持 `output_type="dense&sparse"`，稀疏向量对专业术语精确匹配比 BM25 还准，可作为第三路加入 RRF
3. **rerank 精排** —— 召回 30 条后用 `gte-rerank` 精排到 8 条
4. **年份/被引/tier 加权** —— 综述类问题优先高被引，前沿类问题优先近三年
5. **论文级摘要预生成** —— 离线给 195 篇各生成一段结构化摘要（研究对象/方法/关键数值/结论）存进 db，回答时先看摘要再看片段，能显著提升"跨论文对比"类问题的质量
